<span class="topic-title">Landscape：基于 Rust 和 eBPF 的软路由系统实现</span>
</summary>

<div class="topic-content" markdown="1">

<div class="topic-article" markdown="1">

### 核心内容
作者从 OpenWrt 崩溃和配置繁琐出发，用 Rust 和 eBPF 从零实现了软路由系统 Landscape，并开源在 GitHub。系统重点解决 PCDN 偷上行、IPv6 地址更新、多设备分流等问题。

### 关键要点
- **NAT 设计**：借鉴 Tailscale 打洞机制，通过限制端口复用强制 P2P 回退中继，从而抑制 PCDN 偷上行，同时允许全锥行为以支持正常 P2P。
- **IPv6 支持**：处理 DHCPv6 客户端不响应 reconfigure 的问题，通过发送 preferred lifetime=0 的 RA 报文让客户端丢弃旧前缀；支持 IPv6 NPT，多网口时自动替换前缀；可固定后缀并配合 DDNS 更新运营商 DNS 记录。
- **分流与容器化**：将容器出口作为一等公民，使用 tproxy 解耦，不同规则组 DNS 缓存隔离，支持 Fake IP 处理 Anycast，科学工具只处理必要流量，降低故障影响。
- **其他特性**：前后端分离，提供 API 控制；配置可导出为单文件恢复；TUI 工具支持热备份恢复，无需重启。

### 评论补充
- 有评论建议加入 DPDK，作者回应家用功耗过高，可能考虑 AF_XDP。
- 关于 IPv6 旧前缀问题，评论指出 SLAAC 下可通过设置 preferred lifetime=0 解决，作者确认现有实现已采用此方法。
- 有用户询问 PCDN 抑制的具体方法，作者未在评论中详细展开。

### 核心内容
用户反馈在 Windows 上使用 Codex 进行 vibe coding 时卡顿，配置为 14600K、96G 内存、2080Ti 22G。多位用户指出卡顿主要源于 Codex 客户端本身的设计问题，而非本地硬件性能不足。

### 关键要点
- **磁盘与内存占用**：Codex 每个对话会生成数百 MB 至 1GB 以上的 JSON 文件，切换对话时读写频繁，导致卡顿。
- **MCP 服务开销**：每个会话会启动一套 MCP 服务，配置多时切换对话会启动十几个进程，显著拖慢性能。
- **Windows 特有优化问题**：Codex 对 Windows 优化不佳，可能涉及 WSL 文件系统读写慢、winmgmt 进程占用高、内存泄露等。
- **建议方案**：使用 CLI 模式、避免使用 MCP、将缓存移至 Linux 文件系统、或切换至 macOS（用户反馈 Mac 上更流畅）。

### 评论补充
- 有用户实测 macOS 下 Codex 仍存在内存占用过高问题（24G 本子占用 100G+）。
- 部分用户推荐替代工具如 Zacp、zcode，或使用 ChatGPT 网页版（但网页版内存占用也高）。
- 核心结论：本地硬件对 Codex 性能影响小，主要瓶颈在客户端软件和磁盘 I/O。
